## 1. 占用条卡顿、vsync、把采样挪出热路径

### 现象

CPU / GPU 条子跟着帧在抖；主循环空转轮询，掉帧时条子还会跳一下。

### 做了什么

- GPU / 温度 / 电池 / Wi-Fi 网卡 **路径只发现一次**，之后只读文件。
- 采样、`nmcli` fork 放到 **present 之后**，不和占用条挤同一帧。
- 插值 `dt` 封顶约 33 ms，避免一帧卡住后条子瞬移。
- vsync：`poll(kms + 触控)`，不再 4 ms 空转。`hud_gl_set_poll()`。

扫描走 **GBM + EGL + GLES2**（Adreno 530），失败才回退 CPU `write(/dev/fb0)`。

## 3. 掉帧量化，以及电池 ADC 把循环拖到 ~800 ms

### 现象

性能统计写 `/run/gemini-hud-perf.txt`，掉帧打 kmsg。热路径上 `sample_batt()` 读 `current_now` 每次 **790–900 ms**（高通 QPNP ADC / I2C）。

### 做了什么

热路径只读 `capacity` + `status`。  
`current_now` / `voltage_now` **只在启动时读一次**（瓦数会过时，但不再卡帧）。

修后约 10 s：平均约 17.3 ms，没有 `slow batt`。仍可能有约 1.6% 的 ~33 ms（`nmcli` 解析）。

## 5. CPU / GPU 数字更新过快

### 现象

曾经按帧轮询，CPU / GPU 约 **200 ms** 一采，数字跟插值所以每帧都在跳。

## 6. 开机显示在连 `gemini-…-5G`，实际是 `HomeNet-5G`

### 现象

HUD 启动时像在连 `gemini-HomeNet-5G`。空口上连的一直是 **HomeNet-5G**。

### 根因

`gemini-wifi-connect.sh` 曾经把 NetworkManager **配置名**做成 `gemini-$SSID`（例如 `gemini-HomeNet-5G`）。  
`nmcli device` 的 CONNECTION 是配置名，不是广播 SSID。HUD `parse_info` 把它写进 `wifi.ssid`。  
`iw station dump` 也没有 SSID。

机上当时还有多份 autoconnect 配置：

```text
HomeNet-5G                 yes   （正在用，SSID 正确）
gemini-HomeNet             yes
gemini-HomeNet-5G          yes
gemini-OtherNet-5G          yes
```

开机 NM 可能先激活 `gemini-*` 那份，HUD 就把配置名画出来。`iw dev wlp1s0 link` 里的 SSID 始终是 `HomeNet-5G`。

### 做了什么

1. HUD `apply_wifi_ssid()`：若以 `gemini-` 开头则剥掉前缀。
2. `wifi_link()` 改跑 `iw dev IFACE link`，`parse_link` 解析 `SSID:`。
3. 连接脚本不再用 `gemini-` 前缀，配置名就是 SSID；连接前删掉旧的 `gemini-$SSID`。
4. 机上把那三个 `gemini-*` 的 **autoconnect 关掉**（写在 userdata 的 NM 配置里，重启还在）。

`iw` 实测：已关联到 `wlp1s0` 上的 `HomeNet-5G`（接入点 BSSID 已省略）。

## 9. 其余采样也改成 1 秒一次

CPU / GPU 已经 1 秒一采之后，主循环里还留着一套 **按帧 round-robin**（约 60 fps / 8 步 ≈ **每秒 7～8 次**）：电池、信号、uptime、网卡 sysfs、IP。

全部收进同一拍 `t_occ`（1 秒）：

| 1 秒一次 | 来源 |
|----------|------|
| CPU / 每核 / GPU / 内存 / 温度 | `/proc/stat`、busy sysfs、`/proc/meminfo`、thermal |
| 上下行 | `/proc/net/dev` 的 `wlp1s0` RX/TX 字节差 |
| 电池容量 / 充电状态 | psy `capacity` + `status`（ADC 仍只启动读一次） |
| 信号 | `/proc/net/wireless` |
| 已运行 | `/proc/uptime` |
| 网卡是否还在、IP、网关、MAC | sysfs + ioctl + `/proc/net/route` |
| NM 连接摘要 | `nmcli device`（job，不挡绘制） |

仍跟帧走的只有：触控、`poll_job`、sheet / 占用条插值、绘制。  
可用网络列表打开后仍约 **8 秒**扫一次（那是扫描，不是显示刷新）。

## 10. 上传 / 下载读数实测（局域网）

接口：`wlp1s0`，`/proc/net/dev` 冒号后第 1 列 RX、第 9 列 TX（和 HUD `sscanf` 一致）。

编译主机起临时 HTTP，手机拉 4MB、再 POST 2MB：

| 方向 | RX 增量 | TX 增量 |
|------|---------|---------|
| 下载 4MB | ≈ 4378 KiB | ≈ 66 KiB（ACK） |
| 上传 2MB | ≈ 107 KiB | ≈ 2184 KiB |

方向没有读反。空闲时 SSH 自己也会有每秒几十 KB，所以卡片很少长期停在 `0.0 KB/s`。

公网 speedtest URL 在这台机上容易卡住，测速请走局域网。

## 13. Ubuntu netplan + NetworkManager 1.54：密码对了也不连

### 现象

点别的热点立刻退出面板，日志里是 `secrets were required but not provided`。  
明明刚输入过密码，再点加入还要密码。切到 **R80H** 之类的网会先显示已连接，过一会自己回到 **HomeNet-5G**。

### 根因（机上核对过）

这台 Ubuntu 26.04 的 Wi-Fi 档案不在 `/etc/NetworkManager/system-connections/`（空的），而在：

- `/run/NetworkManager/system-connections/netplan-NM-*.nmconnection`
- `/etc/netplan/90-NM-*.yaml`

`nmcli connection up` **不会用 keyfile 里的 PSK**，除非再传 `passwd-file`。日志：`password ... not given in 'passwd-file'`。  
`nmcli device wifi connect` 会复用一份没有密钥的档案，HUD 又没有 secret agent。  
`connection show --active` 把 **activating** 也算已连；脚本里 `nmcli up` 返回 0 就 `echo 已连接`，无线电其实还在旧网上。NM 失败后 autoconnect 回 CMCC。

### 做了什么

连接脚本 `rootfs-overlay/usr/local/sbin/gemini-wifi-connect.sh`：

- 空密码：读存档 PSK，用 **`passwd-file`** 做 `connection up`。不要把 `device wifi connect` 当主路径。
- 有密码：`connection modify` 原地改 PSK（`psk-flags=0`），再 `up ... passwd-file`。不要先删再建（会丢掉刚存的密码）。
- **`live_ok` / `wait_live`**：设备 STATE 必须是 `connected`（不是 `connecting`），且扫描 IN-USE 行的 SSID 等于目标。测试里 `GEMINI_WIFI_WAIT=0`。
- 存档 PSK 握手失败 → `密码不对，请再试一次`，**exit 3**（不是 NEED_PASSWORD / exit 2）。
- 错误只看本次 `ATTEMPT` 文件，不 grep 整个 `/var/log/gemini-wifi.log`。
- `fail_explain()`：找不到网络 / 连接超时 / 网卡不匹配 / 没拿到地址 / 未能加入此网络。

纯逻辑头文件 `initramfs/gemini-wifi-flow.h`（HUD 和单测共用，无 I/O）：`gw_already_on`、`gw_allow_join`、`gw_on_connect_job`、`gw_display_ssid`、`gw_join_fell_back`、`gw_classify_fail` 等。

主机单测：`bash tests/wifi-flow/run.sh`（`test-wifi-flow.c` + `test-gemini-wifi-connect.sh` + `fake-nmcli`）。

## 15. 「正在忘记…」转个不停

### 现象

点「忘记此网络」后一直显示正在忘记，不会很快变成「已忘记此网络」。忘记按理是点一下就删档。

### 根因

`wifi_forget()` 在扫描占用 `job_pid` 时把 `forgetting=1` 并排队。扫描结束后 `kick_pending` 再调 `wifi_forget`，但 **`forgetting` 仍为 1，函数立刻 return**，删除 job 永远不启动。  
脚本旧路径还会先 `radio wifi on` 再删档，更慢。详情页在 `forgetting==1` 时也不让再点一次。

### 做了什么

- `gw_forget_can_start()`：没有 job 时即使 `forgetting==1` 也允许真正启动忘记。
- 点忘记立刻 **SIGTERM 打断**扫描 / 信息 / 连接 job（子进程 `setpgid`，杀进程组）。
- 脚本 `ACTION=forget` 提到最前：不开关电台，`nmcli -w 3 connection delete`，并按 UUID/SSID 扫掉 netplan 那份档案。
- 若正在用这张网，再 `nmcli device disconnect`，避免无线电挂着旧关联。

## 16. 第一次点连接就提示无法加入

### 现象

从已连的 CMCC 去加另一张网，第一次点连接（或输完密码）很快变成「未能加入此网络 / 无法连接」。再试有时又能连上。

### 根因

切网时 **旧热点会再挂几秒**（有意不先断开，对齐 iOS）。两处把这当成失败：

1. HUD `join_wait_live`：脚本一旦报成功，若  **2.5 秒**内 live SSID 还是旧网，就判 `gw_join_fell_back` 失败。
2. 确认阶段 `connecting=1`，主循环不再跑 `wifi_info`；`parse_info` 也在 connecting 时不排队 `iw link`。于是 **确认窗口里根本看不到新 SSID**，只能等到 2.5 秒误判。
3. 空密码探测：`nmcli up` 返回 0 但无线电还在旧网时，脚本走 `fail_explain` → 「未能加入」，而不是要密码。

### 做了什么

- 确认成功只认 **live SSID == 目标**。还在旧网上时继续等，**最长约 12 秒**才超时；超时若仍在旧网，文案带「已回到 xxx」。
- 确认期间 info ↔ link 继续轮询（`join_wait_live` 时 `want_link` / `want_info`）。
- 点加入会打断正在跑的扫描，连接马上开始，不必等完 25 秒 rescan。
- 空密码路径：`up` 成功但 `wait_live` 失败且不是密码不对 → 落到 `NEED_PASSWORD`，不再直接「未能加入」。

## 17. 忘掉之后列表里还闪一下「已连接」

### 现象

点忘记、回到列表，那一行（或主卡片）还会暂时显示已连接，过几秒才消掉。

### 根因

忘记成功只在 `selected_ssid == wifi.ssid` 时清 `wifi.connected`。随后 `want_info` / `want_scan` / 每秒 `sample_link()` 会把状态刷回来：

- NM 还没断开时 `device` 仍是 `connected`
- 扫描 IN-USE 仍是 `*`
- `sample_link()` 看到网卡 `operstate=up` 且还有 IPv4 就再把 `wifi.connected=1`

### 做了什么

- 一点忘记立刻清该 SSID 的 `connected` / `ssid` / IP / `aps[].active`。
- `forget_ssid` 占位：在真正断开或出现**另一张** live SSID 之前，忽略这份网的 IN-USE、info「已连」、link 残留。
- `sample_link()` **只更新 IP，不再根据「有地址」把状态改成已连接**（已连接只信 NM + `iw`）。
- 脚本在删档后若 IN-USE 仍是这张网，立刻 `device disconnect`。
